# Assumptions

1. Currency. Single currency, amounts have at most 2 decimal places. The maximum amount is 9,999,999,999,999,999.99 (fits `NUMERIC(18,2)`).
2. Money format. Requests accept the amount as a JSON number or a numeric string. Responses always return money as a string with 2 decimals (`"150.00"`) to avoid floating-point rounding in clients.
3. IDs. Accounts, transactions and transfers use UUIDs generated by the database. A malformed ID in the path or body returns 400; a well-formed ID that does not exist returns 404.
4. Account fields. Only `name` is accepted on create. `id`, `balance` and `created_at` are system-generated; sending any of them (or any unknown field) returns 400 rather than being silently ignored, so the client is not left thinking the value was applied.
5. Names. Leading/trailing spaces are trimmed; a name made only of spaces is treated as empty. Names do not have to be unique.
6. description is optional (max 500 characters). reference_id is required, trimmed, 1–100 characters.
7. Transaction type must be exactly `credit` or `debit` (lowercase).
8. Duplicate reference_id. A repeat of an existing `(account_id, reference_id)` returns `409 DUPLICATE_TRANSACTION` with the original transaction in `details`, even if the amount or type differs. Nothing is created and the balance does not change. The duplicate check runs before the balance check, so retrying a debit that already succeeded returns 409, not "insufficient balance".
9. Rejected requests are not stored. Failed or rejected transactions (insufficient balance, validation errors, duplicates) are not recorded in the ledger. The brief only requires that they not affect the balance; storing them would also make "balance = sum of transactions" harder to reason about.
10. Insufficient balance returns `422 Unprocessable Entity`: the request is valid but cannot be processed in the account's current state. Validation errors use 400.
11. Overdraft. Balances can never go below 0. A debit equal to the full balance is allowed.
12. History. Sorted by `created_at` newest first; if two rows share a timestamp, the one inserted later comes first. Default `page=1`, `limit=20`, maximum `limit=100`. A page beyond the last page returns an empty `data` list (not an error). `total_pages` is 0 when there are no transactions.
13. Immutability is enforced at both levels: there are no update/delete endpoints, and the database rejects `UPDATE`/`DELETE` on ledger tables. Balances on `accounts` are only changed by the service, inside the same commit as the ledger row that explains the change.
14. Transfers. `POST /transfers` creates one transfer record plus two ledger transactions (a debit on the source, a credit on the destination) linked by `transfer_id`. The ledger entries get system references (`transfer:<id>:out` / `transfer:<id>:in`); the client's `reference_id` must be unique per source account. Source and destination must differ.
15. Authentication is out of scope for this assignment; every endpoint is public.
16. Timestamps are stored and returned in UTC (ISO 8601).
